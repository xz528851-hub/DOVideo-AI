# 异步投递链路实测记录

## 目的

用本机真实请求测出两个数字，替换掉简历里无法自证的说法：

1. **提交分析接口的响应时间**（异步化的收益侧）
2. **一次完整分析的总耗时**（说明"变快的只是接口，不是计算"）

## 环境

| 项目 | 值 |
| :--- | :--- |
| 机器 | AMD Ryzen 7 7735H (8C/16T)，13.7 GB RAM，Windows 11 25H2 |
| 后端 | Java 21 + Spring Boot 3.5.9 + Undertow，本机启动，端口 9090 |
| 中间件 | Docker Desktop 中的 MySQL 8 / Redis 7.4 / MinIO / Qdrant / RocketMQ 5.3.4 |
| 模型 | 硅基流动 DeepSeek-V3.2 + BAAI/bge-m3 |
| 测试素材 | 自建 20 秒 1280x720 测试视频（0.18 MB，画面含可被 OCR 识别的英文文字，音轨为纯音调） |

## 方法

- 用 `HttpClient` 复用 TCP 连接发起请求，避免每次新建进程/连接的开销污染数据。
- 每个接口先预热 1 次，再串行采样，避免并发互相干扰。
- 以 `/health`（服务端几乎零处理）作为**测量底噪**，用于扣除本地回环与客户端开销。
- 完整分析耗时取自内置遥测接口 `/analysis/agent-trace` 的 `stageDurationMs`，不是客户端掐表。

## 结果

### 1) 接口响应时间

| 接口 | HTTP | 最小 | 中位 | 均值 | 样本 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| `/health`（底噪，服务端零处理） | 200 | 1.4 ms | 2.1 ms | 2.4 ms | 20 |
| `/media/list`（鉴权 + MySQL） | 200 | 5.7 ms | 6.2 ms | 6.2 ms | 20 |
| `POST /analysis/ai` 幂等/复用拦截路径 | 200 | 6.9 ms | 8.6 ms | 8.9 ms | 20 |
| **`POST /analysis/ai` 真实投递路径（202）** | 202 | **26.0 ms** | **27.0 ms** | **27.0 ms** | 3 |
| 超出配额被限流（429） | 429 | 17.4 ms | — | — | 2 |

扣除底噪（约 2 ms）后，**真实投递路径的服务端处理约 25 ms**，其中包含：
1 次 Redis 幂等占位 + 2 次 Redisson 令牌桶获取 + 1 次 RocketMQ 同步发送（等待 Broker SEND_OK）。

### 2) 上传链路（对照，说明上传本身不是瓶颈）

| 步骤 | HTTP | 耗时 |
| :--- | ---: | ---: |
| 上传 0.18 MB 单分片 | 200 | ~532 ms（含测试工具开销） |
| 合并成完整视频（边合并边算 MD5） | 200 | ~686 ms |

### 3) 一次完整分析的总耗时（同一份 20 秒视频，3 个不同目标）

| 目标 | 总耗时 | 模型调用 | 输入/输出 Token | 阶段分解 |
| :--- | ---: | ---: | :--- | :--- |
| 整理视频中的关键信息并生成要点 | 65.7 s | 6 | 4362 / 1090 | 上下文 3.8s、Planner 9.0s、Executor 24.8s、Critic 22.9s、Replanner 8.7s |
| 这一次完整分析要跑多久 | 110.5 s | 5 | 3859 / 1150 | Planner 16.2s、Executor 45.7s、Critic 48.4s |
| 用三句话总结这个视频 | 164.9 s | 6 | 4947 / 1300 | Planner 10.3s、Executor 97.4s、Critic 37.0s、Replanner 20.0s |

比例失衡明显：**接口 27 ms 对任务 60–165 s，相差约三个数量级**，且耗时几乎全部来自大模型推理，而非视频处理本身。

## 结论与口径

可以说的：

- 提交接口响应时间 **约 27 ms**（本机、串行 3 次、已扣底噪）。
- 同一时刻完整分析需要 **分钟级**（本次 20 秒素材为 66–165 秒），异步化**不改变计算耗时**，改变的是"谁在等"。
- 上传链路本身就是毫秒级，不是被异步化的对象。

需要说清的边界：

- 这是**本机单实例、无并发**的测量，不是压测，不能外推为生产吞吐能力。
- 完整分析耗时与视频长度正相关（20 秒素材已需 66 s 以上，长课程视频会更久），因此简历上不宜写死分析耗时数字。
- 模型推理延迟波动大（三次样本 66 / 110 / 165 s），如需更稳的结论应增加样本并统计 P50/P95。

## 复现方式

1. 启动中间件与后端（见仓库 README）。
2. 生成素材：`ffmpeg -f lavfi -i "color=c=white:s=1280x720:d=20:r=10" -f lavfi -i "sine=frequency=440:duration=20" -vf "drawtext=fontfile='C\:/Windows/Fonts/arial.ttf':text='TEST':fontcolor=black:fontsize=72:x=(w-text_w)/2:y=(h-text_h)/2" -c:v libx264 -crf 32 -pix_fmt yuv420p -c:a aac -shortest test.mp4`
3. 走分片上传接口入库，再对同一 mediaId 提交不同目标的 `/analysis/ai` 请求。
4. 用 `/analysis/agent-trace` 读取阶段耗时。

注意事项：用户级限流为 5 次/分钟，真实投递路径每提交一个新目标消耗 1 次配额，超限返回 429。
